# Maze Game – Claude Code Brief

Oct 27, 2026 · @Cesar

## Goal & constraints

Build a browser-based maze game for YouTube Playables that earns about EUR 200/month from YouTube's in-game ads. It is the first of three games sharing one code shell (maze, block puzzle, flow connect), so the shell is built to host more generators later.

- One developer, built with Claude Code; no art team, no backend

- Everything generated by code: mazes, levels, daily challenge

- PEGI 3 content, designed to appeal to adults as much as kids

- Short sessions (1–3 min) that players repeat, plus one daily reason to return

- Must pass Playables certification: YouTube SDK only, no external ads, purchases, analytics or links

- Ships as a single ZIP of static HTML/JS/CSS, under a few MB, runs on mobile and desktop

## Tech stack & project setup

Keep it plain web tech so the ZIP is small, certification is simple, and Claude Code can work on it without a framework fight.

| Item        | Choice                                                                                               | Why                                                              |
|-------------|------------------------------------------------------------------------------------------------------|------------------------------------------------------------------|
| Language    | TypeScript, built with Vite                                                                          | Fast builds, single-bundle output, Claude Code handles it well   |
| Rendering   | HTML5 Canvas 2D (no game engine)                                                                     | Mazes are grids; a 2D canvas is enough and keeps the bundle tiny |

| Repo layout | /src/shell (shared), /src/games/maze (this game), /public (assets), /dist (build output = the ZIP)   | Second and third games drop into /src/games/                     |
| Tooling     | ESLint, Prettier, Vitest for the generator and seed logic                                            | Daily-seed determinism is worth a unit test                      |
| Dev preview | vite dev in the browser, with a mock ytgame object when the SDK is absent                            | Lets you play locally before the Playables test harness          |

## YouTube Playables requirements

The game is a static index.html bundle that loads YouTube's ytgame SDK before any game code and talks to YouTube only through it. These are the calls the shell must wrap; everything is from the [SDK reference](https://developers.google.com/youtube/gaming/playables/reference/sdk) and the [monetization requirements](https://developers.google.com/youtube/gaming/playables/certification/requirements_monetization), both read 2026-10-27.

| Area         | SDK call                                                               | Rule                                                                                                     |
|--------------|------------------------------------------------------------------------|----------------------------------------------------------------------------------------------------------|
| Loading      | ytgame.game.firstFrameReady() then ytgame.game.gameReady()             | Both mandatory; gameReady only once the game is interactable, never while a loading screen shows         |
| Environment  | ytgame.IN_PLAYABLES_ENV                                                | Fork behaviour: inside Playables use YouTube save; outside use localStorage with a mock ytgame           |
| Save/load    | ytgame.game.saveData(str), ytgame.game.loadData()                      | One JSON string, max 3 MiB; keep progress, streak, settings in it                                        |
| Audio        | ytgame.system.isAudioEnabled(), ytgame.system.onAudioEnabledChange(cb) | Initialise from the first; must update on the second; never add an in-game toggle that overrides it      |
| Pause/resume | ytgame.system.onPause(cb), ytgame.system.onResume(cb)                  | Stop the loop, timer and audio on pause, save state; resume may never come                               |
| Interstitial | ytgame.ads.requestInterstitialAd()                                     | Only at natural transitions (level complete, game over), never during play; no guarantee it shows        |
| Rewarded     | ytgame.ads.requestRewardedAd(rewardId)                                 | Strictly opt-in via a labelled button; gameplay must never be blocked behind it; resolves true if earned |
| Score        | ytgame.engagement.sendScore({value})                                   | One integer dimension; pick "best daily time" or "levels cleared" and stay consistent                    |
| Language     | ytgame.system.getLanguage()                                            | Use this, not navigator.language; English first, strings in one file for later locales                   |
| Errors       | ytgame.health.logError(), logWarning()                                 | Call from a global error handler                                                                         |

Also required for certification:

- No external scripts, analytics, ad SDKs, outbound links or purchases of any kind

- Monetization settings switched on in the Developer Portal once ads are integrated

- Title, description and imagery must meet YouTube's advertiser-friendly guidelines

- Pass the [Playables Test Suite](https://developers.google.com/youtube/gaming/playables/reference/test_suite_guide) before submitting

- Stability, accessibility and design requirements live under the [publishing requirements](https://developers.google.com/youtube/gaming/playables/certification/requirements); Claude Code should read that index before the final build

Open question: apply directly for a Playables Developer Portal channel, or publish through a partner such as Playgama (faster, revenue share). Decide before the first submission; the code is the same either way.

## Shared shell (reused by games 2 and 3)

The shell is everything that is not the puzzle itself. It is built first, as its own module, and the maze plugs into it through one small interface. Block puzzle and flow connect later implement the same interface.

| Module      | What it does                                                                                                                                                                                      |
|-------------|---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| platform.ts | Wraps every ytgame call above; provides a mock when outside Playables so vite dev works                                                                                                           |
| storage.ts  | One SaveState object (levels cleared, best times, streak, last daily date, settings); JSON to saveData or localStorage                                                                            |
| rng.ts      | Seeded random (mulberry32 or similar). Daily seed = integer from the UTC date, so every player gets the same daily puzzle; level seed = world + level number, so levels are stable across devices |
| daily.ts    | Daily challenge: today's seed, countdown to the next one, streak count (consecutive UTC days with a daily clear)                                                                                  |
| screens.ts  | Home, Level select, Play, Level complete, Daily result, Settings. Simple DOM overlays on top of the canvas                                                                                        |
| ads.ts      | Two helpers: interstitialAfterLevel() with a frequency cap, and rewarded(rewardId) returning true/false                                                                                           |
| audio.ts    | Tiny sound bank; obeys the Playables mute state                                                                                                                                                   |
| ui/         | Shared theme tokens (colours, fonts, button styles) so the three games look like one studio                                                                                                       |

Game interface every game implements:

interface PuzzleGame {  
id: string; // "maze"  
generate(seed: number, difficulty: number): Level;  
render(ctx: CanvasRenderingContext2D, level: Level, state: PlayState): void;  
input(event: PointerEvent \| KeyboardEvent, state: PlayState): void;  
isSolved(state: PlayState): boolean;  
hint(state: PlayState): void; // what a rewarded ad unlocks  
}

Shell rules:

- Timer and streak logic live in the shell, never in the game

- Difficulty is a number 1–100 the shell passes in; the game decides what it means

- The shell owns all ad calls; a game only says "level done" or "hint requested"

## Maze game design

A small character is guided from the entrance to the exit of a generated maze, as fast as possible. Levels grow in size and add mechanics; the Daily Maze is the same for everyone and ranked by time.

**Generator**

- Recursive backtracker on a grid (perfect maze, one solution) for worlds 1–2; add loops by knocking out 5–15% of walls from world 3 so there are decisions, not just dead ends

- Grid sizes by difficulty: 7×7 (level 1) up to 25×25 (level 100); always odd, always fits the screen without scrolling

- Exit is placed at the far end of the longest path so every maze feels worth it

- Generator is pure: same seed + difficulty = same maze; unit-tested

**Controls**

- Swipe or drag: the character slides in that direction until a wall or junction (like a sliding puzzle), which makes a 25×25 maze playable with a thumb

- Arrow keys / WASD on desktop

- Path trail drawn behind the character; a wrong turn is visible at a glance

**Worlds and mechanics** (20 levels each, unlock in order)

| World       | Theme                   | New mechanic                             |
|-------------|-------------------------|------------------------------------------|
| 1 Garden    | Hedges, daylight        | None, learn the controls                 |
| 2 Cave      | Dark, torch glow        | Fog of war: only nearby cells visible    |
| 3 Ice       | Pale blue, frozen walls | Loops in the maze; keys and locked doors |
| 4 Neon city | Dark with glowing paths | One-way arrows on some cells             |
| 5 Clockwork | Brass, gears            | Walls that shift every few seconds       |

**Daily Maze**

- One maze per UTC day, 15×15 to 19×19, built from the date seed; mechanics from whichever world the player has reached

- Timer; result screen shows today's time, best time, and the streak

- Streak counts consecutive days with a clear; a missed day resets it unless a rewarded "streak shield" was used

**Scoring**

- Stars per level: 3 for under par time, 2 under 1.5× par, 1 for any clear; par comes from the solution length

- Score sent to YouTube = total levels cleared (simple, always rising)

**Visuals and feel**

- Flat, bright, high-contrast shapes; rounded walls; one accent colour per world

- Character is an abstract blob with eyes, animated with a squash on each move

- Small particle burst and sound on exit; confetti on a new best time

- Everything drawn in code, no bitmap art, so the bundle stays small

- Must look good on a 390×844 phone portrait and on a desktop window

## Ad placements

Three placements, all through the YouTube SDK, each at a point the rules allow. Rewarded ads are favours the player chooses; interstitials sit between screens.

| Placement      | Type         | Reward ID          | When                                                                | Cap                                                                                           |
|----------------|--------------|--------------------|---------------------------------------------------------------------|-----------------------------------------------------------------------------------------------|
| Level complete | Interstitial | —                  | After the result screen, before the next level loads                | Not on levels 1–5; then at most one every 3 level completes or 90 seconds, whichever is later |
| Show the way   | Rewarded     | maze-hint-path     | Button on the Play screen: reveals the next 8 cells of the solution | Once per level                                                                                |
| Streak shield  | Rewarded     | maze-streak-shield | Offered on the Daily result screen when the streak is 3 or more     | Once per day                                                                                  |
| Skip level     | Rewarded     | maze-skip-level    | Button on the result screen after 2 failed attempts (over 3× par)   | Once per level                                                                                |

Rules the code must enforce:

- Never request an interstitial during play or while the timer runs

- Every rewarded button has a clear label ("Watch ad to reveal path") and a visible way to continue without it

- Treat requestRewardedAd resolving false or throwing as "no reward", with no penalty

- The interstitial cap is stored in SaveState so it survives reloads

- Outside Playables the mock resolves instantly so testing is fast

## Build plan

Six milestones, each one Claude Code session or two, each ending with something you can play in the browser. Keep the order: the shell and a playable world 1 come before any polish.

1.  **Project + shell skeleton.** Vite/TS project, folder layout, platform.ts with the mock, storage.ts, rng.ts with tests. Done when vite dev shows a blank canvas and the mock ytgame logs firstFrameReady/gameReady.

2.  **Maze generator + play loop.** Generator with tests, canvas render, swipe/keys, win detection, timer. Done when you can clear a 7×7 and a 25×25 on your phone.

3.  **Screens + progression.** Home, level select, result screen, 100 levels across 5 worlds (mechanics for worlds 1–2 only), stars, save/load. Done when progress survives a reload.

4.  **Daily Maze + streak.** Date seed, countdown, streak logic, daily result screen, sendScore. Done when two devices get the same daily maze.

5.  **Ads + Playables compliance.** ads.ts, the three placements with caps, pause/resume, mute handling, error logging, build to a ZIP, run the Playables Test Suite. Done when the test suite passes.

6.  **Worlds 3–5 + polish.** Loops, keys/doors, one-way cells, shifting walls, sounds, particles, world themes. Done when a stranger plays five levels without asking how it works.

After milestone 5 the game is submittable; worlds 3–5 can ship as an update. Target: milestones 1–5 in about four weekends.
